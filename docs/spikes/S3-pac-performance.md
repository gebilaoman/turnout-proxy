# S3：5000+ 条规则 PAC 的页面加载耗时

日期 2026-09-28 · Chrome 154.0.8037.58（macOS，Apple Silicon） · Node 24.18 · 脚本 `spikes/s3-node.js`、`spikes/s3-chrome.js`、`spikes/lib/pacgen.js` · 原始输出 `raw/raw-s3-*.txt`

## 结论

**与假设一致：按域名后缀查哈希表的 PAC 在 4.3k–50k 条规则下，页面加载与直连没有可测差异。无需进一步优化。**
线性逐条正则（竞品常见写法）在 2 万条时每个页面多出约 180ms，证明了"禁止线性匹配"这条规则的必要性。

## 规则样本

- 真实 GFWList（2026-09-28 下载，4485 行）按 ARCHITECTURE §4 的规则粗编译：MATCH 4315、EXCEPT 31、REGEX 1、丢弃 17。
  当前 GFWList 本身不到 5000 条，所以另外合成了 5k / 20k / 50k 条域名做压力测试。
- 对照组：同样的域名，每条生成一个 `/(^|\.)domain$/` 正则逐条匹配。

## Node / V8 单次求值（20000 次调用取平均）

| PAC | 体积 | 编译 | 单次 `FindProxyForURL` |
| --- | --- | --- | --- |
| 哈希 GFWList | 75 KB | 2.4 ms | 0.77 µs |
| 哈希 5k | 131 KB | 1.6 ms | 0.81 µs |
| 哈希 20k | 535 KB | 5.6 ms | 0.62 µs |
| 哈希 50k | 1352 KB | 16.5 ms | 0.63 µs |
| 哈希 GFWList + 200 条正则 | 84 KB | 1.9 ms | **27 µs** |
| 线性 GFWList | 104 KB | 4.3 ms | 600 µs |
| 线性 5k | 170 KB | 6.7 ms | 796 µs |
| 线性 20k | 690 KB | 31.8 ms | 5279 µs |

哈希查找与规则条数无关（O(域名层数)）。开销主要来自 REGEX 列表：200 条正则让单次调用从 <1µs 涨到 27µs，仍可接受，
所以 ARCHITECTURE 里的上限 200 条合理，不建议放宽。

## Chrome 实测页面加载

测试页含 200 张图，分布在 200 个不同主机名上（每个主机名都要单独调用一次 PAC）：150 个不命中走 DIRECT（`--host-resolver-rules` 映射到本机），
50 个命中规则走本地代理。每组先加载 1 次（含 PAC 首次解析），再测 7 次取中位数。200 张图全部加载成功，50 个命中请求全部经代理。

| 配置 | PAC 体积 | `proxy.settings.set` | 首次加载 | 中位加载 | 范围 |
| --- | --- | --- | --- | --- | --- |
| direct（无 PAC） | — | 95 ms | 765 ms* | 223 ms | 165–331 |
| PAC 仅 50 条 | 1 KB | 8 ms | 249 ms | 221 ms | 206–257 |
| 哈希 GFWList | 76 KB | 7 ms | 274 ms | 234 ms | 219–292 |
| 哈希 20k | 535 KB | 26 ms | 293 ms | 254 ms | 208–290 |
| 哈希 50k | 1353 KB | 62 ms | 236 ms | 215 ms | 207–223 |
| 线性 GFWList | 105 KB | 7 ms | 267 ms | 242 ms | 220–362 |
| 线性 20k | 692 KB | 34 ms | 549 ms | **403 ms** | 379–534 |

\* 第一组包含浏览器冷启动，首次加载数字不具可比性。

哈希组之间的差异（±20ms）在噪声范围内。`proxy.settings.set` 即使 1.3MB 也只要 62ms，切换模式/出口不会有体感延迟。

## 给 core/pac 的实现提示（spike 中踩到的坑）

1. **ASCII 转义要分上下文**：`\uXXXX` 只在字符串、正则字面量里合法。第一版我把整段文本里的非 ASCII 连同换行一起转义，结果生成了非法 JS。
   正确做法：只在生成字符串字面量时转义（`JSON.stringify` 后再把 >0x7E 的字符转 `\uXXXX`），代码本身只用 ASCII。
2. **正则用 `new RegExp("<JSON 字符串>")` 输出**，不要拼 `/.../` 字面量——GFWList 的正则里本来就有 `\/`，再转义一次就会生成非法字面量。
3. 查表用 `hasOwnProperty`，不要用 `table[host]`：PAC 里的对象字面量带原型链，主机名后缀逐级剥到 `constructor` 这类键时会误命中。另外规则里若出现 `__proto__` 作为域名，要在编译阶段丢弃。
4. 50k 条时 PAC 为 1.3MB，`chrome.proxy` 没有报大小限制；规则缓存存 `storage.local` 时注意 10MB 配额（`unlimitedStorage` 不在权限白名单里），按目前规模完全够用。
